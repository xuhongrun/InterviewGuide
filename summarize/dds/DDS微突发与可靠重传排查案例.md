# DDS 微突发与可靠重传排查案例

> 状态：`draft`（2026-10-10）
> 性质：公开教学案例。内容已改为 Publisher、Relay、Consumer 等中性角色，不代表任何特定公司或量产系统。参数必须在公开实验环境重新生成后，才能升级为 `verified`。

## 1. 问题模型

一个高频 `Publisher` 通过 DDS 向 `Consumer` 发送可变大小的数据。正常负载下链路稳定；业务对象数量突然增加时，Consumer 的数据更新会短暂停滞，负载下降后自行恢复。

可能的因果链是：

```text
业务数据瞬时增加
  -> Publisher 在极短时间内集中 write
  -> 网卡、交换机或接收端出现微突发
  -> UDP/RTPS 数据丢失
  -> RELIABLE 链路发送 Heartbeat/AckNack 并重传
  -> 新数据和修复流量竞争带宽与发送窗口
  -> Consumer 观察到长尾延迟或数据停滞
```

这只是待验证假设。出现“卡顿”时，也可能是序列化、锁竞争、CPU 调度、接收回调阻塞或业务线程积压，不能只凭相关性认定网络是根因。

## 2. 分层排查

### 2.1 建立统一时间线

在 Publisher、Consumer 和网络侧统一时钟，记录：

- 业务对象数、序列化后样本大小和 `write()` 调用速率。
- Publisher 写入耗时、阻塞次数、发送队列深度。
- Consumer 接收序号、回调耗时、业务队列深度。
- 网卡吞吐、丢包、Socket buffer drop 和交换机端口统计。
- RTPS Heartbeat、AckNack、Gap、Data/DataFrag 的时间与序号。

只有当“业务突发、网络丢包、RTPS 修复和应用停滞”在同一时间线上对应，才能继续验证该假设。

### 2.2 排除主机内部瓶颈

建议同时观察：

```bash
pidstat -t -p <pid> 1
sar -n DEV 1
ss -u -a -m
perf top -p <pid>
```

重点排除：

- Listener 中执行耗时业务。
- 有界队列已满导致 Publisher 阻塞。
- CPU 被其他实时线程抢占。
- 序列化和内存分配耗时激增。
- Consumer 收到数据，但业务处理线程没有及时消费。

### 2.3 分析网络与 RTPS

在可控环境使用交换机镜像口或两端抓包，至少统计：

- 1 ms、10 ms、100 ms 窗口内的峰值速率，而不仅是秒级平均带宽。
- UDP 校验错误、内核接收丢包和交换机队列丢弃。
- Heartbeat/AckNack 频率和重传字节数。
- RTPS 分片大小、同一 Sample 的 DataFrag 数量和修复范围。

平均带宽没有打满并不能排除微突发。反过来，出现 AckNack 也不自动证明它是应用停滞的根因。

## 3. MTU、RTPS 分片与 IP 分片

必须区分三个概念：

1. **以太网 MTU**：常见值 1500 字节，通常表示单个 IP packet 可承载的最大长度，不包含 Ethernet header。
2. **UDP payload**：IPv4 无选项时理论上限通常为 `1500 - 20 - 8 = 1472` 字节；IPv6 基本头下通常为 `1500 - 40 - 8 = 1452` 字节。还要为 RTPS header/submessage 和安全开销留空间。
3. **RTPS fragmentation**：DDS 可以把一个大 Sample 拆成多个 `DATA_FRAG`。RELIABLE 模式下，接收端可通过 NackFrag 请求缺失的 RTPS fragment。

不要把 RTPS fragment 与 IP fragmentation 混为一谈。IP 层通常不会像 RTPS 一样提供选择性可靠重传；丢失一个 IP fragment 可能导致整个 IP datagram 无法重组。

因此，“单片 1480 字节一定安全”或“丢一个分片只重传该 IP 分片”都不是通用结论。实际 fragment size 应结合：

- IPv4/IPv6、VLAN 和安全封装。
- DDS/RTPS header 开销。
- 厂商实现与传输配置。
- 路径 MTU 探测与抓包结果。

## 4. 候选修复方案

### 4.1 发送端整形

如果证据表明确有微突发，可以评估厂商 Flow Controller、异步发布或应用层有界发送队列。目标是限制短时间窗口内的峰值，而不是只限制秒级平均速率。

需要验证的副作用：

- 平均延迟是否增加。
- P99/P99.9 是否改善。
- 队列满时采用阻塞、丢旧还是丢新。
- 控制数据是否被大数据 Topic 阻塞。

### 4.2 调整 RTPS 分片

较小 fragment 可以降低单次修复代价，但会增加 header、调度和 Ack/Nack 管理开销。较大 fragment 有利于吞吐，却可能增加突发和丢失后的修复量。

正确选择来自参数扫描，而不是固定经验值。例如在公开实验中比较多个 fragment size，并记录：

- 有效吞吐和包速率。
- CPU 使用率。
- 丢包率和重传比例。
- 端到端 P50/P99/P99.9 延迟。

### 4.3 限制可靠性资源

联合检查：

- History 与 Resource Limits。
- Reliable Writer 的发送窗口和最大阻塞时间。
- Reader 的接收缓存和处理能力。
- 同一传输上的 Topic 优先级与流量隔离。

RELIABLE 不代表无限缓存，也不代表永不丢失。达到资源限制时的行为取决于 QoS、API 调用方式和厂商实现。

### 4.4 其他方案

- 增大 Socket buffer：可以吸收短暂突发，但可能增加排队延迟，且不能替代源端整形。
- 提升链路带宽：可能缓解瓶颈，但软件仍可能制造更高峰值。
- 切换 TCP：提供拥塞与流量控制，但会引入队头阻塞等不同权衡，不能简单归纳为“实时性一定差”。
- 拆分 Topic 或优先级：避免大数据修复流量阻塞控制与状态数据。

## 5. 验证修复

修复验收不使用“看起来不卡了”作为标准。至少比较修改前后：

| 指标 | 目的 |
|---|---|
| 1/10/100 ms 峰值带宽 | 判断微突发是否被削平 |
| UDP/Socket/交换机丢包 | 判断丢包发生在哪一层 |
| RTPS 重传字节占比 | 判断可靠修复是否被放大 |
| P50/P99/P99.9 端到端延迟 | 防止平均值掩盖长尾 |
| Writer/Reader 队列深度 | 判断瓶颈是否转移 |
| CPU、上下文切换、RSS | 评估修复成本 |

测试需要覆盖正常、峰值、持续过载、随机丢包和 Consumer 降速等场景，并验证恢复时间。

## 6. 面试表达模板

公开面试表达应讲方法，不讲雇主内部细节：

> 我处理过一个与数据量突增相关的 DDS 长尾延迟问题。先将业务量、进程资源、网络丢包和 RTPS 修复报文放到统一时间线，排除了 CPU 与业务线程阻塞后，确认短时间窗口内的发送突发会触发接收侧丢包，并在 RELIABLE 模式下放大修复流量。随后通过发送端整形、分片参数扫描和可靠性资源上限控制降低峰值，并以 P99 延迟、重传比例和队列深度做回归。公开版本只保留方法论，具体模块、参数和数据已移除。

面试官继续追问时，可以解释：

- 如何证明是因果关系而不是时间相关。
- 如何区分应用积压、Socket 丢包和交换机丢包。
- RTPS fragmentation 与 IP fragmentation 的区别。
- 为什么平均带宽不足以识别微突发。
- 修复方案如何影响平均延迟和长尾延迟。
