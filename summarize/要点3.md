## CPU/内存突增
1. **定位问题进程**
> top/ps命令
   ```bash
   top                         # 实时监控（按P/M排序）
   ps aux --sort=-%cpu | head  # 显示CPU Top进程
   ps aux --sort=-%mem | head  # 显示内存Top进程
   ```

2. **深入分析目标进程**
   - **CPU分析**
     ```bash
     top -H -p <PID>          # 查看线程级负载
     pidstat -p <PID> 1 5     # 进程CPU采样
     vmstat 1                 # 检查上下文切换(cs)和中断(in)
     ```
   - **内存分析**
     ```bash
     pmap -x <PID>            # 内存映射详情
     smem -k -P <进程名>      # 可视化内存分布
     dmesg -T | grep -i oom   # 检查OOM Killer记录
     ```

3. **系统级检查**
   ```bash
   iotop                     # 磁盘I/O分析
   nethogs                   # 进程网络流量
   sar -P ALL 1 3            # 多核CPU利用率
   grep CRON /var/log/syslog # 定时任务检查
   ```
### 高频原因速查表
| **资源类型** | **TOP 5 常见原因** |
| --- | --- |
| **CPU暴增** | 1. 死循环/无限递归<br>2. 线程阻塞/锁竞争<br>3. 算法复杂度剧增<br>4. 频繁GC（Java等）<br>5. 恶意挖矿程序 |
| **内存暴增** | 1. 内存泄漏（未释放对象）<br>2. 缓存失控（如Redis）<br>3. JVM堆配置不合理<br>4. 大文件加载/处理<br>5. 内存型数据库溢出 |

| **类别** | **可能原因** |
| --- | --- |
| **CPU** | 死循环、无限递归、算法复杂度暴增、线程阻塞/锁竞争、频繁GC（Java）、恶意挖矿程序 |
| **内存** | 内存泄漏（未释放对象）、缓存失控（如Redis）、JVM堆配置不合理、大文件加载 |
| **系统级** | 频繁缺页中断（swap使用激增）、僵尸进程累积、内核Bug、硬件故障（内存条/CPU过热） |
| **外部因素** | DDoS攻击、爬虫洪水请求、备份任务启动、配置错误（如线程池过大） |

### **自动化工具推荐**
1. **`perf`**
   系统性能分析：`perf top -p <PID>`
2. **`strace`**
   跟踪进程系统调用：`strace -p <PID> -T -f -o strace.log`
3. **`bpftrace`**
   动态内核追踪：`bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[comm] = count(); }'`

### 重要注意事项
1. **快速缓解**
   ```bash
   kill -STOP <PID>         # 暂停异常进程（保留现场）
   sync; echo 3 > /proc/sys/vm/drop_caches  # 释放缓存
   ```
2. **根治方法**
   - 代码优化：修复死循环/内存泄漏
   - 配置调整：限制进程资源（cgroups）
   - 架构改进：增加熔断机制/负载均衡

> **黄金法则**：先定位进程 → 分析线程 → 结合日志 → 验证代码逻辑。保留现场数据（`core dump`/`jstack`）后再重启服务。


## 静态库与动态库
| 特性         | 静态库 (`.lib`, `.a`)                     | 动态库 (`.dll`, `.so`, `.dylib`)             |
| :----------- | :---------------------------------------- | :------------------------------------------- |
| **链接时机** | 编译/链接时（代码复制到EXE）              | 运行时（由OS加载链接）                       |
| **打包方式** | 代码嵌入到可执行文件中                    | 独立于可执行文件存在                         |
| **运行时依赖** | 无                                        | 有（需特定版本库文件）                       |
| **部署**     | 简单（只需EXE）                           | 较复杂（需EXE+库文件或确保系统有库）         |
| **EXE大小**  | 大                                        | 小                                           |
| **内存占用** | 高（库代码在多进程中不共享）              | 低（库代码在内存中可被多进程共享）           |
| **库更新**   | 必须重新编译链接并发布整个EXE             | 替换库文件即可（需二进制兼容）               |
| **模块化/插件** | 困难                                      | 天然支持（显式链接）                         |
| **加载方式** | 随主程序启动加载                          | 隐式链接（启动时加载）或显式链接（运行时加载）|
| **版本管理** | 简单（固化在EXE中）                       | 复杂（需机制保证兼容性，易发“DLL Hell”）     |

*   **选择静态库：**
    *   需要程序完全独立，避免部署依赖问题（如小工具、命令行程序）。
    *   对启动速度要求极高（省去运行时加载库的时间）。
    *   使用的库非常小或改动极其频繁，且不希望影响其他程序。
    *   对内存占用不敏感。
    *   目标环境对动态库的管理或兼容性有严重问题。
*   **选择动态库：**
    *   库非常大，多个程序共享使用（如系统API、大型框架如Qt/GTK、C运行时库）。
    *   需要节省磁盘空间（多个程序共享一个库文件）和内存（共享代码段）。
    *   需要独立更新库（Bug修复、安全补丁）而不想重新编译和分发所有主程序。
    *   需要实现插件系统或运行时模块加载。
    *   库由第三方提供且只提供动态库版本。

> 在实际项目中，常常是**混合使用**：核心、稳定且体积小的模块可能静态链接，而大型、共享或需要独立更新的模块则动态链接。操作系统本身大量使用动态库来提供服务。


## 大数据量、高频率场景下，DDS协议栈如何保证低延时、高可靠

**总结：DDS如何应对大数据量、高频率、低延迟、高可靠挑战**

1.  **架构基础：** 去中心化、直接通信、UDP传输奠定了低延迟的物理基础。
2.  **核心机制：** 可配置的`RELIABILITY` + `HISTORY` + 端到端重传/确认 + 大消息分片 提供了高可靠性的保障。
3.  **性能优化：** 零拷贝传输、异步发布、高效的CDR序列化、`TRANSPORT_PRIORITY` 直接优化数据传输路径，最小化延迟。
4.  **资源与流控：** `RESOURCE_LIMITS`, `TIME_BASED_FILTER`, 内容过滤订阅 有效管理资源（内存、CPU、网络带宽），防止过载，确保系统在高负载下稳定运行。
5.  **实时监控与保障：** `DEADLINE`, `LATENCY_BUDGET` 提供了监控和保障实时性的手段。
6.  **快速启动与恢复：** 高效的发现协议和`DURABILITY`（尤其是`TransientLocal`）确保了新节点或故障节点恢复后能快速获取最新数据并参与通信。

**关键配置要点：**

*   **合理设置`HISTORY`深度：** 足够大以容纳预期的突发丢包和允许新订阅者获取数据，但又不能大到耗尽内存。
*   **调整`RESOURCE_LIMITS`：** 确保发送/接收队列、缓存池足够大，避免因资源不足导致的阻塞或丢包。
*   **利用`TIME_BASED_FILTER`和内容过滤：** 这是应对高频率更新的关键武器，显著降低无关数据处理的开销。
*   **选择异步发布：** 提高发布者吞吐量。
*   **考虑`TRANSPORT_PRIORITY`：** 为关键数据分配更高优先级。
*   **优化网络基础设施：** 使用低延迟交换机和网卡，配置适当的QoS策略，确保网络路径畅通无阻。组播的支持对于大规模部署非常重要。
