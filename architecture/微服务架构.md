# 微服务架构

> 与 SOA 同源、更细粒度。本篇覆盖拆分、通信、数据一致性、治理与运维。

---

## 1. 微服务 vs 单体 vs SOA

| 维度 | 单体 Monolith | SOA | **微服务** |
|------|------|------|------|
| 部署单元 | 一个 | 大粒度服务 | 小粒度服务 |
| 通信 | 进程内调用 | ESB / SOAP | **REST / gRPC / MQ** |
| 数据 | 共享 DB | 共享或独立 | **各服务独立 DB** |
| 团队 | 大团队同代码库 | 业务团队 | **小团队全栈自治（2-pizza team）** |
| 治理 | 编译期 | ESB 集中 | **去中心化 + 服务网格** |
| 适用 | 早期 / 小流量 | 企业整合 | 高变更频率 / 大规模 |

口诀：**单体先做对，微服务再做大**；过早拆分 = 分布式单体。

---

## 2. 拆分原则

* **DDD 限界上下文（Bounded Context）** 是首要边界。
* **业务能力**而非技术分层（不要按"所有 Controller / 所有 DAO" 拆）。
* **单一职责 + 数据自治**：每个服务有自己的数据库，禁止跨服务直接访问表。
* **粒度**：能独立发布、独立扩缩容、独立故障；2~3 周一次大变更。
* **Strangler Fig** 模式：在单体外围逐步剥离，旧路由 → 新服务，最终下线单体。

反模式：

* **分布式单体**：拆成多个服务但仍同进度发布、共享 DB。
* **闲聊型服务**：A 调 B 调 C 调 D，链路过深、延迟叠加。
* **过细拆分**：纳米服务（nano-services），运维成本压垮收益。

---

## 3. 服务间通信

| 同步 | 异步 |
|------|------|
| **REST/HTTP** —— 通用、调试方便 | **消息队列**（Kafka / RabbitMQ / Pulsar / NATS） |
| **gRPC** —— 强类型、HTTP/2、多语言 | **事件总线 / Event Bus** |
| **GraphQL** —— BFF 聚合层 | **CQRS + Event Sourcing** |

选择：

* 查询、低延迟、需要返回 → **同步**。
* 事件驱动、解耦、削峰、跨域 → **异步**。
* 大多数项目混用：核心同步 RPC + 边缘事件流。

**API Gateway**：统一入口（鉴权、限流、路由、聚合）；典型方案 Kong / APISIX / Envoy / Spring Cloud Gateway。

---

## 4. 数据一致性

放弃强一致，拥抱**最终一致性**（CAP 定理：分布式只能 CP 或 AP，PA 牺牲）。

| 模式 | 适用 |
|------|------|
| **Saga（编排 / 编排）** | 多服务事务，每步有补偿动作 |
| **TCC（Try-Confirm-Cancel）** | 资金 / 库存类强约束 |
| **Outbox 模式** | DB + 消息可靠投递（事务表 + 后台扫描发 MQ） |
| **CQRS + Event Sourcing** | 写读分离，事件作为唯一真相 |
| **2PC / XA** | ⚠️ 低性能、易阻塞，微服务一般不用 |

口诀：**业务允许补偿就 Saga；强一致才 TCC；可靠发件用 Outbox**。

---

## 5. 服务治理

* **服务注册/发现**：Consul / etcd / Nacos / Eureka / K8s Service。
* **配置中心**：Apollo / Nacos / etcd / Consul KV，支持灰度、回滚。
* **负载均衡**：L4（HAProxy / IPVS）+ L7（Envoy / Nginx），算法 RR / Least Conn / EWMA / 一致性哈希。
* **熔断 / 限流 / 降级**：Sentinel / resilience4j / Hystrix（已停更）/ Envoy 限流。
* **服务网格 Service Mesh**：Istio / Linkerd —— Sidecar 模式把治理与业务剥离。
* **统一鉴权**：OAuth2 / OIDC / JWT；网关侧统一颁发与验证。

---

## 6. 可观测性 Observability

三大支柱缺一不可：

| 维度 | 工具 |
|------|------|
| **Metrics** | Prometheus + Grafana；RED / USE 指标 |
| **Logs** | Loki / ELK / EFK；结构化 JSON |
| **Traces** | OpenTelemetry → Jaeger / Tempo / Zipkin |

* **W3C TraceContext**（`traceparent`）跨服务/语言透传。
* 统一 SDK：**OpenTelemetry**（OTel）—— 取代 OpenTracing / OpenCensus。
* 关键面板：服务依赖拓扑、错误率分桶、长尾延迟、上下游 SLO 燃尽。

---

## 7. 部署与发布

* **容器化默认**：Docker + K8s（Deployment / StatefulSet / Job）。
* **不可变基础设施**：镜像即制品，禁止登录改文件。
* **GitOps**：Argo CD / Flux，仓库即真相。
* **发布策略**：
  * **滚动 Rolling**：默认。
  * **蓝绿 Blue/Green**：双环境瞬时切换。
  * **金丝雀 Canary**：按权重渐进切流（Argo Rollouts、Flagger）。
  * **影子 Shadow**：复制生产流量到新版本只读验证。
* **特性开关 Feature Flag**：LaunchDarkly / Unleash / 自研，发布与启用解耦。

---

## 8. 弹性 Resilience

* **超时 + 重试 + 退避 + jitter**：见 [网络 最佳实践](../network/网络%20最佳实践.md)。
* **熔断 Circuit Breaker**：连续失败开断路，半开探测，恢复闭合。
* **舱壁 Bulkhead**：线程池/连接池隔离，避免一个慢依赖拖垮全部。
* **限流 Rate Limit**：令牌桶 / 漏桶；网关 + 服务双层。
* **降级 Fallback**：核心保留、非关键返回缓存或默认值。
* **故障演练 Chaos Engineering**：Chaos Mesh / Gremlin；GameDay。

---

## 9. 安全

* **零信任**：内部互调也要鉴权（mTLS + JWT）。
* **mTLS**：Service Mesh 自动签发证书（SPIFFE/SPIRE）。
* **机密管理**：Vault / AWS Secrets Manager / K8s Secret + KMS 加密；**禁止入仓**。
* **依赖供应链**：SBOM、Sigstore 签名、CVE 扫描进 CI。
* **API 安全**：OWASP API Top 10（破坏对象级授权、过度暴露、注入）。

---

## 10. 团队与组织

* **康威定律**：系统结构 = 组织结构。
* **团队拓扑（Team Topologies）**：Stream-aligned、Platform、Enabling、Complicated-subsystem。
* **You build it, you run it**：开发承担运维责任（Amazon 模式）。
* **DORA 4 大指标**：变更交付时长、部署频率、变更失败率、恢复时长。
* 服务必须有 **owner + on-call rotation + SLO/SLA + runbook**。

---

## 11. 反模式 Top 10

1. **共享数据库**：多服务读写同一表。
2. **分布式单体**：拆服务但依赖紧耦合、同发布。
3. **过细拆分**：50 行代码 = 一个服务。
4. **同步链路过深**：A→B→C→D，长尾爆炸。
5. **没有契约测试**：上游改字段下游崩。
6. **无可观测性**：故障靠"打 log 进容器"。
7. **数据一致性靠 2PC** 跨多个外部系统。
8. **API 网关塞业务逻辑**：成为新单体。
9. **每个服务自造轮子**（日志、监控、鉴权）。
10. **没有 SLO**：性能指标"差不多就行"。

---

## 12. Top 15 Checklist

1. ☐ 服务边界基于 DDD 限界上下文，而非技术分层。
2. ☐ 每服务独立 DB，禁止跨服务直接访问表。
3. ☐ API 契约（OpenAPI / Protobuf）入仓 + 契约测试（Pact）。
4. ☐ 同步 RPC + 异步事件混用，按场景选。
5. ☐ 跨服务事务用 Saga / Outbox，不用 2PC。
6. ☐ 服务网格或 SDK 统一治理（熔断/限流/重试）。
7. ☐ OTel 三件套（指标/日志/链路）默认接入。
8. ☐ 网关层统一鉴权 / 限流 / 路由。
9. ☐ K8s + GitOps 部署；金丝雀 + 特性开关。
10. ☐ mTLS 内部互信 + 机密集中管理。
11. ☐ 每服务定义 SLO + on-call + runbook。
12. ☐ 故障演练定期化。
13. ☐ DORA 4 指标看板。
14. ☐ CVE/SBOM 自动扫描。
15. ☐ 服务下线流程：依赖排查 → 灰度切流 → 监控 → 回收资源。

---

## 面试速记

1. **微服务 ≠ 万能**：先单体做对，复杂到瓶颈再拆。
2. **DDD 限界上下文**是拆分核心边界。
3. **数据自治**：每服务独立 DB，靠事件 / API 同步。
4. **CAP**：分区下只能 C 或 A；微服务通常选 AP + 最终一致。
5. **Saga vs TCC vs Outbox**：补偿事务、强一致两阶段、可靠发件。
6. **熔断 / 限流 / 降级 / 舱壁** 防雪崩。
7. **服务网格** 把治理下沉到 Sidecar，业务无感知。
8. **OTel** 取代 OpenTracing / OpenCensus，是事实标准。
9. **金丝雀 + Feature Flag** 发布与启用解耦。
10. **康威定律**：组织决定架构，反之亦然。
