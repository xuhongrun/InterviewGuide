# 分布式系统

> 本篇覆盖 CAP / BASE、一致性模型、共识算法、复制与分区、分布式事务、时间与时钟、典型陷阱。

---

## 1. CAP 与 BASE

* **CAP 定理**（Brewer）：分布式系统在 **网络分区** 发生时，不能同时满足
  * **C** Consistency（一致性，所有节点同时看到同一数据）
  * **A** Availability（可用性，每个请求获得非错误响应）
  * **P** Partition tolerance（分区容忍，必选）
* 现实：网络分区是常态 → **要么 CP（强一致弱可用），要么 AP（高可用最终一致）**。
* **BASE**：Basically Available + Soft state + Eventual consistency —— AP 系统的设计哲学。
* **PACELC**：分区时 PA/PC，正常时 EL（延迟 vs 一致性）。

---

## 2. 一致性模型谱

| 模型 | 强弱 | 说明 |
|------|------|------|
| **线性一致 Linearizable** | 最强 | 全局实时序，等同单机 |
| **顺序一致 Sequential** | 强 | 进程内有序，全局有顺序但不实时 |
| **因果一致 Causal** | 中 | 有因果关系的操作有序（如评论顺序） |
| **读己之写 Read-your-writes** | 弱 | 自己写完自己能读到 |
| **单调读 Monotonic Reads** | 弱 | 不会越读越旧 |
| **最终一致 Eventual** | 最弱 | 静默后所有副本一致 |

口诀：**ATM 强一致、社交动态最终一致**。

---

## 3. 共识算法 Consensus

* **Paxos**（Lamport）：理论奠基，难懂；Multi-Paxos / Fast Paxos 是工程化变体。
* **Raft**（Ongaro 2014）：易懂等价于 Multi-Paxos；分 Leader 选举 / 日志复制 / 安全性 / 集群成员变更。
  * 状态：Follower / Candidate / Leader
  * 任期 Term + 日志索引 → 全序日志
  * 多数派提交（quorum = ⌊N/2⌋+1）
* **ZAB**（ZooKeeper）：原子广播；类 Paxos。
* **Viewstamped Replication**：与 Paxos/Raft 等价。
* **PBFT / HotStuff**：拜占庭容错（区块链场景）。

应用：

| 系统 | 算法 |
|------|------|
| etcd / Consul / TiKV / CockroachDB | Raft |
| ZooKeeper | ZAB |
| Spanner | Paxos + TrueTime |
| Kafka（≥ 3.3 KRaft 模式） | Raft |

> 普通业务**不要自造共识**，直接用 etcd / ZK。

---

## 4. 复制 Replication

| 策略 | 说明 | 适用 |
|------|------|------|
| **主从同步** | 主写后同步到从，主等所有从 ACK | 强一致、低吞吐 |
| **主从异步** | 主写完即返回，后台同步 | 高吞吐、有数据丢失风险 |
| **半同步** | 主等任一从 ACK | 折中 |
| **多主 Multi-Master** | 任一节点可写，需冲突解决（CRDT / LWW） | 多活、写冲突复杂 |
| **无主 Leaderless** | Dynamo 风格，W+R>N 保证一致 | Cassandra、Riak |

**Quorum 公式**：N=副本数，W=写副本数，R=读副本数，**W + R > N** 保证读到最新写。

---

## 5. 分区 Sharding

* **范围分区**：按 key 区间（如时间）；易热点。
* **哈希分区**：均匀但范围查询慢。
* **一致性哈希**：节点增减只迁移 1/N 数据；典型 Cassandra / Memcached。
* **目录分区**：路由表集中维护（HBase Region Server）。

挑战：**重分片**、**跨分片事务**、**分布式 join**。

---

## 6. 分布式事务

| 方案 | 一致性 | 性能 | 复杂度 |
|------|------|------|------|
| **2PC（两阶段提交）** | 强 | 慢、阻塞 | 中 |
| **3PC** | 强 | 慢 | 高（实际少用） |
| **TCC** | 强 | 快 | 高（业务侵入） |
| **Saga** | 最终 | 快 | 中（编排/编排） |
| **Outbox + MQ** | 最终 | 快 | 低 |
| **Spanner / Calvin（确定性事务）** | 强 | 中 | 极高（基础设施级） |

口诀：**业务可补偿 → Saga；钱财强约束 → TCC；可靠投递 → Outbox**。

---

## 7. 时间与时钟

* **物理时钟漂移**：NTP 同步典型 ±10ms，无法用作分布式排序。
* **逻辑时钟 Lamport Clock**：单调递增，捕获因果但不能比较并发事件。
* **向量时钟 Vector Clock**：能识别并发与因果（Dynamo 用）。
* **HLC（Hybrid Logical Clock）**：物理 + 逻辑混合，CockroachDB / YugabyteDB 用。
* **TrueTime**（Google Spanner）：原子钟 + GPS，提供时间区间，等待区间过去即可全序。

教训：**永远不要假设时钟单调**；NTP 调时可能回拨。

## 8. 故障与失败模式

| 故障 | 描述 |
|------|------|
| **崩溃停止** | 节点挂了，最简单 |
| **崩溃恢复** | 重启后状态可能丢失 |
| **遗漏 Omission** | 消息丢失 |
| **拜占庭** | 节点撒谎/恶意（区块链场景） |
| **网络分区** | 部分节点互相不可达 |
| **慢节点 Tail Latency** | 没挂但很慢，比挂了还坏（"灰故障"） |
| **时钟漂移** | 物理时钟跳跃 |

应对：

* **Heartbeat + 超时检测**（误判风险）
* **Phi accrual failure detector**（自适应阈值）
* **Hedged Request**（同时请求多副本，要最快的）
* **Backup Request / Tied Request**（Tail at Scale 论文）

---

## 9. 消息可靠性

* **At-most-once**：可能丢，不会重复。UDP 风格。
* **At-least-once**：不丢，可能重复。常见，需消费者**幂等**。
* **Exactly-once**：理论上不可能，只能在闭环系统内做到（Kafka 事务 + 幂等生产者 + 消费位点事务提交）。

实现幂等：**业务唯一键 + 去重表 / Redis SETNX / 状态机校验**。

## 10. 一致性 vs 可用性的工程取舍

| 业务 | 偏好 |
|------|------|
| 银行核心账务 | CP（不可用胜过算错钱） |
| 电商下单库存 | CP + 限流降级 |
| 商品列表 / 评论 | AP（最终一致足矣） |
| 社交动态 | AP（读己之写 + 最终一致） |
| 在线游戏战斗 | AP（一致性靠重发与对账） |
| 配置中心 | CP（etcd/ZK） |
| DNS | AP（最终一致 + TTL） |

## 12. 反模式 Top 10

1. 假设**网络可靠**（八谬误第 1 条）。
2. 用**物理时间排序**事件。
3. 跨服务用 2PC 做强一致。
4. 消费者**不幂等**还要求 exactly-once。
5. **Quorum 配 W=R=1**：副本只是冗余，不保一致。
6. 共识系统部署 **2 节点**（多数派 = 2，挂一台就停摆）。
7. 心跳超时设得太短 → **抖动级"故障"**。
8. **重试无退避 + 无 jitter** → 故障期同时重试形成踩踏。
9. 分布式锁用 **Redis SETNX 不带 fencing token**（Redlock 争议）。
10. 不做**故障演练**，第一次故障即首次发现。

## 13. 八谬误 Fallacies of Distributed Computing

新人**至少错信 3 条**：

1. 网络可靠
2. 延迟为零
3. 带宽无限
4. 网络安全
5. 拓扑不变
6. 只有一个管理员
7. 传输成本为零
8. 网络是同质的

## 14. Top 15 Checklist

1. ☐ 业务明确选择 CP 还是 AP，并写文档。
2. ☐ 共识用现成系统（etcd/ZK），不自造。
3. ☐ 副本数 ≥ 3 且为奇数，部署跨可用区。
4. ☐ Quorum 配置满足 W+R>N。
5. ☐ 消费者全幂等（业务唯一键）。
6. ☐ 分布式事务优先 Saga / Outbox，2PC 慎用。
7. ☐ 不依赖物理时钟排序（用 HLC / 单调 ID）。
8. ☐ 重试 = 退避 + jitter + 幂等。
9. ☐ Hedged / Tied Request 治理长尾。
10. ☐ 监控副本滞后、leader 切换次数、quorum 健康。
11. ☐ Schema 演化兼容（Protobuf / Avro 向后向前）。
12. ☐ 故障演练：网络分区、节点挂、磁盘满、时钟跳。
13. ☐ 限流 + 熔断 + 降级 + 舱壁。
14. ☐ 数据备份 + 异地容灾 + RTO/RPO。
15. ☐ 跨可用区 / 跨地域延迟模型清楚。

## 面试速记

1. **CAP**：分区下 C/A 二选一；现实多选 AP + 最终一致。
2. **BASE / PACELC**：CAP 的工程延伸。
3. **共识首选 Raft**：Leader 选举 + 日志复制 + 多数派。
4. **Quorum**：W+R>N 保证读到最新。
5. **CRDT** 解决多主写冲突。
6. **物理时钟不能用作排序**，用 Lamport / Vector / HLC。
7. **Exactly-once 不存在**，只能闭环 + 幂等近似。
8. **2PC 阻塞、Saga 最终一致、TCC 强约束**。
9. **Tail at Scale**：长尾比挂掉更坏，hedged request 治理。
10. **八谬误** 新人第一课。
