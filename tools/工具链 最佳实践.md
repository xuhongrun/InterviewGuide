# 工具链 最佳实践

> 涵盖 Git、Repo、SQLite3 以及通用研发工具链（编辑器、Shell、容器、密钥）。

---

## 1. Git

### 1.1 仓库与分支

* **主分支**：`main`（默认）；保护分支必开 PR review + CI 通过。
* **分支模型**：
  * **Trunk-Based Development**（推荐）：小步提交直接合 main，配 Feature Flag。
  * **GitHub Flow**：`feature/*` → PR → main，一日多发布。
  * **Git Flow**：含 `develop`/`release`/`hotfix`，重型，传统软件适用。
* **分支命名**：`feature/xxx`、`fix/xxx`、`chore/xxx`、`hotfix/xxx`，关联 issue 编号。

### 1.2 提交规范

* **Conventional Commits**：

  ```
  feat(parser): support array literals
  fix(api): handle empty payload
  refactor(core): extract validator
  docs: update install guide
  perf(cache): use lru
  test: add boundary cases
  build: bump deps
  ci: add lint job
  chore: tidy
  ```

* 一次提交一个意图；**不要** "fix typo + 重构 + 加功能" 混在一起。
* commit message 标题 ≤ 72 字符；空行后写动机与影响。
* PR 合并默认 **Squash**（线性历史），保留主干干净。
* 重写历史用 `git rebase -i` —— **只在私有分支**，已 push 的公共分支禁止 force push。

### 1.3 高频命令

```bash
git switch -c feature/x          # 新建并切分支（替代 checkout -b）
git restore --staged file        # 取消暂存（替代 reset HEAD）
git restore file                 # 撤销工作区修改
git stash push -m "wip"          # 临时保存
git rebase -i HEAD~5             # 整理最近 5 次提交
git cherry-pick <sha>            # 摘取提交
git bisect start / good / bad    # 二分查 bug
git reflog                       # 找回"丢失"的提交
git log --oneline --graph --all  # 看分支拓扑
git blame -L 10,20 file          # 行级追溯
git worktree add ../wt feat/x    # 多工作区并行
```

### 1.4 钩子与质量门

* `.pre-commit-config.yaml` 入仓：lint、format、secret 扫描、conventional commit 校验。
* 服务端钩子（GitLab / GitHub Actions）：CI 必过、PR 必有 review、敏感分支签名提交（`git commit -S`）。
* `.gitignore` 严格，**禁入**：`node_modules/`、构建产物、`.env`、IDE 文件、`__pycache__`、`*.log`、密钥/证书。
* `.gitattributes` 设置文本规范化、`text=auto eol=lf`、二进制 `binary`。

### 1.5 大文件与子模块

* 二进制 / 大文件用 **Git LFS**（图片、模型、固件）。
* 子模块 `git submodule` 谨慎使用；推荐 `git subtree` 或单仓多包（monorepo + workspace）。
* monorepo 工具：**Bazel / Pants / Nx / Turborepo**。

### 1.6 反模式 Top 10

1. 直接 push 到 main / master。
2. force push 公共分支。
3. 提交大文件 / 密钥 / 凭证。
4. commit message 写 `fix bug` / `update`。
5. 一个 PR 改 100 文件、混类型。
6. 长寿分支（> 1 周）冲突地狱。
7. 不写 `.gitignore`，仓库塞满构建产物。
8. 用 `git pull` 拉取无 rebase 设置（产生 merge commit 噪声）。
9. `git add .` 不审视就提交。
10. 密钥泄漏后只 delete commit 不轮换密钥。

### 1.7 Top 12 Checklist

1. ☐ 主分支保护 + PR + CI。
2. ☐ Conventional Commits。
3. ☐ pre-commit + secret 扫描。
4. ☐ `.gitignore` / `.gitattributes` 完整。
5. ☐ 大文件 LFS。
6. ☐ Squash 合并保线性。
7. ☐ 短分支寿命（≤ 3 天）。
8. ☐ `git pull --rebase` 默认。
9. ☐ Tag + Changelog 自动生成（release-please / semantic-release）。
10. ☐ 签名提交（GPG / SSH key）。
11. ☐ 定期清理已合并分支。
12. ☐ 紧急回滚预案（revert vs reset 选 revert）。

详见 [git](git.md)。

## 2. Repo（Android / 多仓管理）

* `.repo/manifest.xml` 是真相源；分支固定到 SHA / Tag 才可复现构建。
* `repo init -u <manifest> -b <branch>` → `repo sync -j$(nproc)`。
* `repo forall -c '<cmd>'` 批量执行（慎用，提交前先 `--abort-on-errors`）。
* 团队规范 `repo upload` → Gerrit Review；每次提交独立 Change-Id。
* 镜像加速：`repo init --mirror` 建本地镜像，再 `repo init --reference=<mirror>` 提速。

## 3. SQLite3

### 3.1 工程化要点

* **单进程多线程**：默认 serialized 模式；多进程并发写易冲突。
* **WAL 模式**（强烈推荐）：

  ```sql
  PRAGMA journal_mode = WAL;
  PRAGMA synchronous = NORMAL;   -- 与 WAL 配合，崩溃安全 + 高吞吐
  PRAGMA temp_store = MEMORY;
  PRAGMA mmap_size = 268435456;  -- 256MB
  PRAGMA cache_size = -64000;    -- 64MB（负值=KB）
  ```

* **外键约束** 默认关闭，必须显式：`PRAGMA foreign_keys = ON;`。
* **预编译语句**（`prepare/bind/step`）替代字符串拼接 → 性能 + 防注入。
* **批量插入**用单事务包裹，性能差 100×。

### 3.2 索引与查询

* 主键自带 rowid 索引；查询走 **`EXPLAIN QUERY PLAN`** 检查。
* 避免 `SELECT *`；只取所需列。
* 复合索引顺序遵循查询条件最常用列在前。
* `WITHOUT ROWID` 表适合自然主键，节省存储 + 提速。
* `LIKE 'abc%'` 可用索引；`LIKE '%abc'` 不可。

### 3.3 备份与维护

* 在线备份用 `sqlite3_backup` API 或 `.dump`；不要直接拷文件（可能损坏）。
* `VACUUM;` 整理碎片；上线前在低峰执行；WAL 模式下需先 checkpoint。
* `PRAGMA integrity_check;` 定期跑。
* 数据库文件 **不入 git**；schema 迁移脚本入 git。

### 3.4 反模式

1. 多进程并发写。
2. 长事务 + 高并发读 → 锁争用。
3. 没用预编译语句，SQL 注入。
4. 没开 WAL，写性能差。
5. 表无 PRIMARY KEY。
6. 在循环里 commit。
7. BLOB 大文件直存（建议外部存储 + 路径）。

详见 [SQLite3](SQLite3.md)。

## 4. 通用研发工具链

### 4.1 Shell / 终端

* 默认 **bash + set -euo pipefail**；脚本入仓必过 `shellcheck`。
* 长流程用 **tmux / zellij** 持久会话。
* 替代 / 强化工具：`fd`（find）、`rg`（grep）、`bat`（cat）、`fzf`（模糊查找）、`exa/eza`（ls）、`zoxide`（cd）、`htop/btm`（top）、`ncdu`（du）、`tldr`（man）。

### 4.2 容器

* `Dockerfile` 多阶段、最小基镜像；`HEALTHCHECK` + 非 root 用户。
* `docker compose` 本地复现；CI 用 buildx 多架构镜像。
* 镜像仓库扫描 CVE（Trivy / Grype）；签名 Sigstore cosign。

### 4.3 编辑器 / IDE

* VS Code + 各语言扩展；`.editorconfig` 统一缩进/换行。
* 团队约定 lint/format 配置入仓；不要"个人风格 PR"。
* 大型 C++ 用 `compile_commands.json` 让 clangd 工作；CMake 自动产出。

### 4.4 密钥与凭证

* `.env` 不入仓；用 **`direnv`** / **`1Password CLI`** / **Vault** 注入。
* GitHub Actions 用 OIDC 联合身份，少存长期 Token。
* 仓库扫描 `gitleaks` / `trufflehog` 入 pre-commit + CI。
* 一旦泄漏：**轮换 + 撤销 + 审计访问日志**，不仅是 delete commit。

### 4.5 文档与协作

* README 是仓库门面：定位、安装、运行、贡献、许可证 五件套。
* ADR / Runbook / On-call playbook 入仓。
* Issue / PR 模板降低沟通成本。
* 自动化：CHANGELOG（release-please）、依赖更新（Dependabot / Renovate）。

## 面试速记

1. **Trunk-Based + Feature Flag** 是现代主流分支模型。
2. **Squash + Conventional Commits** 让历史可读、可生成 Changelog。
3. **Force push 公共分支 = 团队事故**。
4. **大文件 LFS**；密钥/构建产物**严禁入仓**。
5. **`git rebase -i`** 整理私有分支，**`git revert`** 修复已发布。
6. **`git bisect`** 二分定位 bug 提交。
7. **SQLite WAL + 单事务批量** 性能差 100×。
8. **EXPLAIN QUERY PLAN** 是 SQLite 调优入口。
9. **pre-commit + secret 扫描** 是默认基线。
10. **密钥泄漏 → 轮换密钥 + 审计**，不要只删提交。
