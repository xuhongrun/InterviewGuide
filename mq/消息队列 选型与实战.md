# 消息队列 选型与实战

> Kafka / RabbitMQ / RocketMQ / Pulsar / NATS / Redis Stream —— 异步解耦、削峰、事件驱动核心组件。

---

## 1. 为什么需要 MQ？

| 场景 | 价值 |
|------|------|
| **解耦** | 生产者 / 消费者独立演进、独立部署 |
| **异步** | 主流程返回快；耗时操作（发邮件、生成报表）异步 |
| **削峰** | 秒杀、突发流量缓冲；防 DB 打挂 |
| **广播** | 一份事件多服务消费（订单创建 → 库存 + 风控 + 推送） |
| **事件驱动** | CQRS / Event Sourcing / Outbox |
| **跨语言** | 解耦协议、多语言团队协作 |

**代价**：增加中间件运维、消息丢失/重复/乱序问题、系统复杂度上升。

---

## 2. 主流 MQ 对比

| | Kafka | RabbitMQ | RocketMQ | Pulsar | NATS / JetStream | Redis Stream |
|---|------|----------|----------|--------|------------------|--------------|
| **核心模型** | 分布式日志 | AMQP / Exchange | 类 Kafka + 事务/延迟 | 计算存储分离（Bookie + Broker） | Pub/Sub + JetStream 持久化 | 内嵌 Stream |
| **吞吐** | 10w~100w/s | 万级 | 10w/s | 10w+/s | 极高（内存） | 高（内存） |
| **延迟** | 毫秒级 | 微~毫秒 | 毫秒 | 毫秒 | 微秒 | 微秒 |
| **持久化** | ✅磁盘日志 | ✅可选 | ✅ | ✅分层存储 | ✅JetStream | ✅但容量小 |
| **顺序保证** | 分区内有序 | 单队列 | 分区内有序 | 分区内有序 | Subject 内 | Stream 内 |
| **事务** | ⚠️有限（exactly-once 困难） | ✅简单 | ✅事务消息 | ✅ | 基础 | 基础 |
| **延迟消息** | ❌（外部方案） | ✅死信 / 插件 | ✅原生分级 | ✅ | ✅ | ❌ |
| **回放** | ✅按 offset / 时间 | ❌（消费即删） | ✅ | ✅按 timestamp | ✅ | ✅ |
| **多租户** | ⚠️ | ✅vhost | ✅ | ✅原生 | ✅Account | ❌ |
| **典型用途** | 日志、流处理、CDC | 业务异步、RPC over MQ | 阿里电商、金融 | 多租 SaaS、流式 | IoT / 边缘 / 微服务 | 轻量级、内嵌 |

**选型决策**：
* 流量大 + 日志/分析 + 流处理 → **Kafka**。
* 业务路由复杂、规模中等、需 RPC 模式 → **RabbitMQ**。
* 中文社区、电商金融、原生事务/延迟 → **RocketMQ**。
* 多租户 + 海量 Topic + 计算存储分离 → **Pulsar**。
* 边缘/IoT / 极低延迟 / 轻量 → **NATS JetStream**。
* 已有 Redis + 业务量小 → **Redis Stream**（不要硬上大流量）。

## 3. Kafka 核心模型

### 3.1 概念

```
Producer → Topic (N 个 Partition) → Consumer Group
                                  ↓
                              Consumer1, 2, 3...
```

* **Partition**：水平扩展单元；每个分区是有序追加日志。
* **Offset**：分区内消息序号。
* **Consumer Group**：组内分区独占消费；扩消费者 ≤ 分区数。
* **Replica**：每分区 N 副本，Leader 读写，Follower 同步；ISR 列表。
* **Controller**：协调 Broker；新版基于 KRaft（去 ZK）。

### 3.2 高吞吐原因

* **顺序磁盘写**（远快于随机）。
* **零拷贝** sendfile：磁盘 → 网卡 不经用户态。
* **批量** + **压缩** （snappy / lz4 / zstd）。
* **页缓存** 借助 OS。
* **分区并行**。

### 3.3 关键配置

| 端 | 配置 | 说明 |
|----|------|------|
| Producer | `acks=all` | 所有 ISR 确认才返回（不丢） |
| | `retries=Integer.MAX_VALUE` + `enable.idempotence=true` | 幂等生产 |
| | `linger.ms=5` `batch.size=64KB` | 批量提升吞吐 |
| | `compression.type=zstd` | 压缩 |
| Broker | `min.insync.replicas=2` | 配合 acks=all |
| | `unclean.leader.election=false` | 防数据丢失 |
| Consumer | `enable.auto.commit=false` | 手动提交 offset |
| | `isolation.level=read_committed` | 读已提交（事务） |
| | `max.poll.records=500` | 单次拉取上限 |

### 3.4 Exactly-Once

* **幂等 Producer**：PID + 序号去重单分区。
* **事务**：跨分区原子写 + 消费 offset 写入同事务（read-process-write）。
* 注意：Kafka EOS 在 Kafka 内有效；写到外部系统仍需业务幂等。

## 4. 三大可靠性问题

### 4.1 消息丢失

| 阶段 | 原因 | 方案 |
|------|------|------|
| 生产者 | 异步发送未确认 | `acks=all` + 重试 + 回调失败处理 |
| Broker | 主从未同步就挂 | 多副本 + `min.insync.replicas≥2` + 关 unclean |
| 消费者 | 拉到就 commit，处理崩溃 | **先处理后提交 offset**；幂等业务 |

### 4.2 消息重复

* 生产端重试 / Broker 故障转移 / 消费端处理后未及时 commit。
* **业务幂等**：唯一键 + DB 去重表 / Redis SETNX / 状态机校验。

### 4.3 消息乱序

* Kafka 仅**分区内有序**；同 key hash 到同分区即可保证业务有序。
* 失败重投会乱序：`max.in.flight.requests.per.connection=1` 或开幂等。
* 业务层加序号字段，消费时按序列处理。

### 4.4 消息积压

排查：消费端慢（DB 慢、外部依赖、GC）/ 消费者数量不足 / 单条耗时。
应急：扩消费者（≤ 分区数）/ 临时新消费组分流到临时 Topic / 增分区（仅未来生效，已有积压不重平衡）。
长期：批处理、预取、降低单条耗时、独立慢路径队列。

## 5. 模式与最佳实践

### 5.1 工作队列（Work Queue）

多个消费者抢消息，每条只被处理一次。RabbitMQ 单队列多消费者；Kafka 同消费组。

### 5.2 发布订阅（Pub/Sub）

一份消息广播到多组。RabbitMQ Fanout Exchange；Kafka 不同 Consumer Group。

### 5.3 路由（Routing / Topic）

RabbitMQ Topic Exchange + 路由键模式（`order.*.created`）。

### 5.4 死信队列 DLQ

消费 N 次失败 → 进入 DLQ 单独处理 + 告警。**生产必备**。

### 5.5 延迟队列

* RabbitMQ：TTL + DLX；或 `rabbitmq-delayed-message-exchange` 插件。
* RocketMQ：原生分级延迟（1s/5s/10s/...）。
* Kafka：外部时间轮 + 重投 / Tombstone。

### 5.6 事务消息（Outbox 模式）

业务表 + outbox 表同事务写 → 单独进程扫 outbox → 投递 MQ → 标记发送。
**避免**双写不一致（DB 成功 MQ 失败）。详见 [架构 最佳实践](../architecture/架构%20最佳实践.md) / [分布式系统](../architecture/分布式系统.md)。

### 5.7 CDC（变更数据捕获）

Debezium 抓 MySQL binlog → Kafka → 下游（搜索 / 缓存 / 数仓）。事件驱动 + 数据复制。

## 6. 简单代码示例

### Kafka Python（confluent-kafka）

```python
from confluent_kafka import Producer, Consumer

p = Producer({"bootstrap.servers": "kafka:9092",
              "acks": "all", "enable.idempotence": True,
              "compression.type": "zstd"})
def cb(err, msg):
    if err: log.error("send fail: %s", err)
p.produce("orders", key=str(uid), value=json.dumps(evt), callback=cb)
p.flush()

c = Consumer({"bootstrap.servers": "kafka:9092",
              "group.id": "billing",
              "enable.auto.commit": False,
              "auto.offset.reset": "earliest"})
c.subscribe(["orders"])
while True:
    msg = c.poll(1.0)
    if msg is None or msg.error(): continue
    try:
        handle(msg)            # 业务幂等
        c.commit(msg, asynchronous=False)
    except Exception:
        log.exception("handle fail; will retry")
```

### RabbitMQ（pika）

```python
import pika
conn = pika.BlockingConnection(pika.URLParameters("amqp://..."))
ch = conn.channel()
ch.queue_declare(queue="email", durable=True,
                 arguments={"x-dead-letter-exchange": "dlx"})
ch.basic_qos(prefetch_count=10)        # 限流
def on(ch, method, props, body):
    try:
        send_email(json.loads(body))
        ch.basic_ack(method.delivery_tag)
    except Exception:
        ch.basic_nack(method.delivery_tag, requeue=False)   # 进 DLQ
ch.basic_consume(queue="email", on_message_callback=on)
ch.start_consuming()
```

## 7. 监控与运维

| 指标 | 含义 |
|------|------|
| **Lag**（消费滞后） | 最关键，超阈值告警 |
| **吞吐 in/out** | bytes/s、msg/s |
| **错误率** | produce / consume / replication 失败 |
| **ISR 数 / under-replicated** | 副本健康 |
| **磁盘使用 / 段大小** | 容量规划 |
| **GC / FD / 网络** | Broker 进程健康 |

工具：Kafka 自带 JMX → Prometheus jmx_exporter；Kafka Manager / Conduktor / Burrow（Lag 专用）；Pulsar Manager；RabbitMQ Management UI。

## 8. 高频面试题

1. Kafka 为什么这么快？（顺序写 + 零拷贝 + 批量 + 压缩 + 分区并行 + 页缓存）
2. Kafka 怎么保证不丢消息？（生产 acks=all + 幂等；Broker min.insync≥2、关 unclean；消费先处理后提交 offset）
3. Kafka 怎么保证消息有序？（同 key 进同 partition；in.flight=1 或幂等）
4. Kafka 与 RocketMQ / RabbitMQ 区别？
5. ZooKeeper 在 Kafka 里作用？KRaft 是什么？
6. Consumer Group rebalance 触发条件？怎么减少抖动？（StickyAssignor、CooperativeRebalance、增大 session.timeout）
7. Exactly-Once 怎么实现？外部系统怎么保证？
8. 消息积压怎么处理？
9. 延迟消息怎么实现？
10. 如何选 partition 数量？（吞吐 / 消费者并行 / 分区越多 leader 切换越慢）
11. 死信队列设计；重试策略（指数退避 + 最大次数）。
12. 业务怎么保证幂等？（唯一键 + 状态机 + 去重表）
13. Outbox 模式解决什么问题？
14. 怎么测试 MQ 系统？（混沌：杀 Broker / 网络分区 / 时钟漂移）

## 9. Top 20 MQ Checklist

1. ☐ 选型基于真实场景（吞吐 / 延迟 / 顺序 / 事务 / 团队栈）。
2. ☐ 生产端：`acks=all` + 幂等 + 重试 + 回调监控。
3. ☐ Broker：副本 ≥ 3，`min.insync ≥ 2`，关 unclean。
4. ☐ 消费端：手动 commit；先处理后提交。
5. ☐ 业务幂等是底线（数据库唯一键 / 去重表 / 状态机）。
6. ☐ 死信队列 + 告警 + 人工处理 SOP。
7. ☐ 消息体小（< 1 MB），大对象走 OSS + 引用。
8. ☐ Schema 版本化（Avro / Protobuf + Schema Registry）。
9. ☐ 分区数预留扩展空间（不易缩）。
10. ☐ Topic 命名规范：`{domain}.{event}.{version}`。
11. ☐ 关键 Topic 独立集群 / 独立 broker，避免互相影响。
12. ☐ 监控 Lag / ISR / 失败率 / 重试次数。
13. ☐ 有限制：限流（prefetch）、超时、批量大小。
14. ☐ 跨机房：MirrorMaker / Cluster Linking；评估 RTO/RPO。
15. ☐ 重要业务用 Outbox / Inbox 模式保数据库与 MQ 一致。
16. ☐ 磁盘容量预警 + 日志保留策略（按时间 + 大小双重）。
17. ☐ 优雅停机：消费者收到信号 → 处理完当前 → commit → 退出。
18. ☐ 升级演练：滚动升级 + 回滚预案。
19. ☐ 安全：TLS + SASL + ACL；多租户用 ACL 隔离。
20. ☐ 故障演练：Kill broker、丢分区、网络分区、磁盘满。

## 面试速记

1. **MQ 三大价值**：解耦 / 异步 / 削峰。
2. **Kafka 快**：顺序写 + 零拷贝 + 批量 + 分区。
3. **不丢**：生产 acks=all + Broker ISR ≥ 2 + 消费先处理后 commit。
4. **不重**：业务幂等（唯一键 / 状态机 / 去重表）。
5. **有序**：同 key 同分区 + 单分区单消费者。
6. **EOS**：幂等 + 事务 + 外部系统幂等。
7. **积压** = 扩消费者 / 增分区 / 优化处理 / 临时分流。
8. **死信** = 失败兜底 + 告警 + 人工。
9. **延迟消息**：RocketMQ 原生 / RabbitMQ TTL+DLX / Kafka 外部时间轮。
10. **Outbox**：业务表 + 出箱表同事务 → 后台投递。
11. **Lag** 是最重要监控指标。
12. **CDC + Kafka** 是事件驱动数据同步标配。
